# Workflow Engine Primitive for the Base Framework

## Context

This repo (`basebackend`) is not a single app — it's a Laravel 13 + Backpack CRUD 4.1 **starting point** that other developers fork/extend to build their own admin-driven software. The ask is to add a workflow engine (states, drag-drop editable flow charts, preconditions, email/notification triggers, timers, parallel branches, per-person task queues) as a *platform primitive*: something any downstream developer can attach to their own Eloquent models without forking the engine itself.

This document is the architecture and design brief for the feature, covering the full scope in one pass rather than a phased v1/v2 split — everything below is in scope. It is not yet a step-by-step build sequence; that follows as a separate, more granular implementation plan once this architecture is agreed.

## Why build vs. buy

Two paths exist. Both were discussed and this one was chosen:

1. **Embed a JS flow-chart library + build a small interpreter in Laravel** (chosen). Keeps everything inside the one Laravel app a downstream dev already has; matches the existing pattern in this repo of shipping self-contained custom Backpack fields (`latlng_picker`, `switch`, `slug`, etc.) rather than pulling in an external service.
2. **Run a dedicated BPM engine (Camunda/Zeebe, n8n) alongside Backpack**, with Backpack only creating/triggering process instances via API. Faster to get enterprise BPM features but forces every downstream project to also deploy, secure, and operate a second service — defeats the point of a self-contained starting point.

Given this is a platform primitive meant to be forked into many downstream projects with varying ops maturity, **path 1** is the right default.

## Package structure & distribution

This ships as a self-contained package at **`packages/workflow`**, mirroring how `packages/backpack/permissionmanager` and `packages/backpack/crud` are structured in this repo — not scattered into `app/`. Concretely:

- **Directory layout** (matching `packages/backpack/permissionmanager/src/{app,config,resources,routes}`): `packages/workflow/src/app/{Models,Http/Controllers,Events,Registries,Actions,Preconditions}`, `packages/workflow/src/config/workflow.php`, `packages/workflow/src/database/migrations` (the six tables from Core data model), `packages/workflow/src/resources/views` (the canvas/inspector Blade+JS, published under a `workflow::` view namespace), `packages/workflow/src/routes/workflow.php`.
- **Namespace & autoload**: `Workflow\` mapped to `packages/workflow/src` — added to `composer.json`'s existing `autoload.psr-4` block alongside the current entries:
  ```json
  "Backpack\\CRUD\\": "packages/backpack/crud/src",
  "Backpack\\Generators\\": "packages/backpack/generators/src",
  "Backpack\\PermissionManager\\": "packages/backpack/permissionmanager/src",
  "Workflow\\": "packages/workflow/src"
  ```
- **`Workflow\WorkflowServiceProvider`** registers the package's migrations, config (mergeable so a downstream app can override individual keys), the `workflow::` view namespace, the standalone canvas/editor routes, and the built-in action/precondition type registrations — added to `config/app.php`'s `providers` array the same way the three Backpack providers are registered today.
- **Everything genuinely engine-level lives in the package**: the `HasWorkflow` trait, `WorkflowInstance`/`WorkflowInstanceToken`/`WorkflowDefinition`/etc. models, the `WorkflowActionType`/`WorkflowPreconditionType` interfaces and registries, the `Transitioning`/`Transitioned` events, the standalone canvas controller, and base Backpack CrudController classes for definitions/instances. A downstream project's `app/` directory stays clean — a dev only touches `app/` to (a) add `use HasWorkflow;` to their own model, and (b), only if they want to customize the admin UI beyond what ships, extend the package's base CrudControllers the same way `app/Http/Controllers/Auth/PermissionCrudController.php` extends behavior from `packages/backpack/permissionmanager` today. Out of the box, with no app-level files at all, the package self-registers working `/admin/workflows/*` routes and sidebar entries.
- **Custom action/precondition types and event listeners a downstream dev writes** naturally still live in their own `app/`, registered from their own service provider — the package only owns the registries, not what gets registered into them.
- **All six workflow tables live on their own SQLite connection, separate from the main application database** — the same isolation pattern this repo already uses for the kitchen sink (`config/database.php`'s `kitchensink` connection, `database_path('kitchensink.sqlite')`). `WorkflowServiceProvider` registers a `workflow` connection the same shape (`'driver' => 'sqlite', 'database' => database_path('workflow.sqlite')`), the package's own migrations run against it, and every workflow model sets `protected $connection = 'workflow';`. This keeps the engine's tables (and its `.sqlite` file) fully decoupled from whatever primary database a downstream project uses — matters even more here than for the kitchen sink demo, since the workflow tables need to reference records that live on the *main* connection (`workflowable_type`/`workflowable_id`), which Eloquent's polymorphic relations handle fine across connections since the reference is just a string class name + id, not a database-level foreign key.

## Testing strategy

This package needs test coverage robust enough that downstream developers can trust it as a foundation, not just a proof of concept. Using Pest (already the project's test framework, v4/PHPUnit 12):

- **Unit tests, no database, for the pure logic** — this is where the highest-risk code lives and where coverage matters most: the precondition tree evaluator (every AND/OR nesting combination, via Pest datasets), the `actor_rule` resolver (role-only, permission-only, named-user-only, and combined `any`/`all` cases), the token engine in isolation (fork spawns N tokens, join only completes once all expected tokens arrive, a join never double-fires), the field-policy resolver (visible/readonly/label/type/custom_field_definition override resolution and default-fallback), the `CustomFieldDefinitionParser` safe-eval whitelist (rejects function calls, variable references, string interpolation, static/object method calls; accepts nested literal arrays and `true`/`false`/`null`), and the action/precondition/event registries (registering, resolving-by-key, and the error case of an unregistered key).
- **Feature tests for every integration point** — the full Backpack CRUD flows (definition list, the canvas save endpoint persisting a new `workflow_definition_versions` row without touching in-flight instances), `transitionTo()` end to end (state change, history row written, `Transitioned` event dispatched — asserted with `Event::fake()`), the email/notification actions (asserted with `Notification::fake()`/`Mail::fake()`, never actually sent), the signed webhook route (valid signature transitions, invalid signature rejected), `WorkflowBulkTransitionOperation` (mixed qualifying/non-qualifying rows in one request, correct summary), and dry-run mode (asserts zero real side effects and zero persisted rows).
- **Versioning-safety regression test** — the specific scenario of editing and republishing a definition while an instance is mid-flow on the old version, asserting the in-flight instance is untouched.
- `phpunit.xml`'s coverage `<include>` currently only covers `./app`; it needs `./packages/workflow/src` added so coverage reporting actually reflects the package once it exists outside `app/`.

## Demo workflow: Purchase Request

A worked example proves the design end to end and gives downstream developers a real reference to copy. The flow, mapped onto this document's graph vocabulary:

| Node | Type | Notes |
| --- | --- | --- |
| `draft` | state | Field policy: requester can edit everything. Entry point; also where a "returned" request lands back for revision. |
| `pending_hod_review` | state | Field policy: HOD sees the request read-only except a remarks field. |
| `department_feedback_fork` | fork | Reached only if the HOD chooses to request feedback (see edges below) — spawns three parallel tokens. |
| `marketing_feedback`, `technical_feedback`, `operations_feedback` | state | One per department; each department's reviewer can edit only their own feedback field. |
| `department_feedback_join` | join | Waits for all three feedback tokens before proceeding automatically to Finance review. |
| `pending_finance_review` | state | Finance sees the request plus a computed remaining-budget field, read-only. |
| `pending_ceo_review` | state | CEO sees the full request, read-only. |
| `approved`, `rejected` | state | Terminal. All fields read-only. |

Edges (illustrative, not exhaustive):
- `draft → pending_hod_review`: manual, `actor_rule: {roles: ['employee']}` — any employee, per the requirement.
- `pending_hod_review → pending_finance_review` ("approve, skip feedback") **and** `pending_hod_review → department_feedback_fork` ("request department feedback"): both manual, both `actor_rule: {roles: ['hod']}` — the HOD's choice of *which button they click* is the branch; no precondition needed, since a person deciding at click time is a simpler and more honest model than an automatic rule guessing intent.
- `pending_hod_review → draft` ("return") and `→ rejected` ("reject"): manual, `actor_rule: {roles: ['hod']}`, `inputs: [{name: 'hod_remarks', type: 'textarea', required: true, store_as: 'hod_remarks'}]`, `requires_confirmation: true` — demonstrates required transition remarks and a confirm prompt together on one edge.
- `marketing_feedback → department_feedback_join` (and the same for technical/operations): manual, `actor_rule: {roles: ['marketing']}` (etc.), `inputs: [{name: 'feedback', type: 'textarea', required: true}]`.
- `department_feedback_join → pending_finance_review`: automatic, fires once all three incoming tokens are consumed — no human clicks this one.
- `pending_finance_review → pending_ceo_review`: manual, `actor_rule: {roles: ['finance']}`, **precondition**: `field_lte` comparing the request's amount against a remaining-budget value — demonstrating that preconditions gate manual edges too (a real budget check can outright hide/disable the approve button, not just gate automatic ones), `surfaces: ['record_button', 'bulk_action']` so finance can approve several small requests at once.
- `pending_finance_review → rejected` / `→ draft`: manual, same actor_rule, same `inputs`/`requires_confirmation` pattern as the HOD's reject/return edges.
- `pending_ceo_review → approved` / `→ rejected` / `→ draft`: manual, `actor_rule: {roles: ['ceo']}`.
- A **timer** on `pending_hod_review`: if untouched for 3 days, an escalation-chain `start_timer` action notifies the HOD's manager — the SLA-escalation showcase.
- Every terminal and rejection/return edge fires a `send_notification` action to the original requester — the plain-notification showcase, alongside the `Transitioned` event any downstream dev could also listen to independently.

This single demo exercises: role-based `actor_rule`, a human choosing between two manual edges as the branching mechanism, fork/join parallel review, a precondition on a manual edge backed by real model data, required transition inputs with `store_as`, `requires_confirmation`, bulk transitions, a timer/escalation chain, and both notification-action and event-listener extension points — deliberately, so it functions as living documentation.

**Ships in its own package and its own database — not the engine package, and not the main app** — for the same reason the engine itself is isolated: this is a demo, and a demo has no business living in `app/` or sharing a database with either the main application or the reusable engine. Mirrors both the engine package's structure and the existing kitchen sink's install/toggle pattern:
- A new package at **`packages/workflow-demo-purchase-request`**, PSR-4 mapped as `WorkflowDemo\PurchaseRequest\` in `composer.json`, with its own `PurchaseRequestDemoServiceProvider`, migrations, seeder, a `PurchaseRequest` model (using the engine's `HasWorkflow` trait — this is also the proof that a model outside the engine package can consume it), and a `PurchaseRequestCrudController` that exercises the `workflow` column/field, the field-policy-driven form, and the bulk-transition operation.
- Its own SQLite connection (e.g. `purchase_request_demo`, `database_path('purchase_request_demo.sqlite')`) — separate from both the main app's database and the engine's own `workflow` connection (the engine's polymorphic instance/token rows will reference this demo's model across that connection boundary, which is itself a good test of the cross-connection polymorphism called out in Core data model).
- Gated behind its own `config('app.workflow_demo')` boolean toggle and its own `php artisan workflow-demo:install [--fresh]` command — exactly the pattern `config('app.kitchensink')` and `kitchensink:install` already establish, so it's optional and disposable for a downstream project that doesn't want the demo at all.

## Design goals for this primitive

- **Model-agnostic.** Any Eloquent model opts in via a trait; the engine has no hardcoded knowledge of "which model" it's running against.
- **Data-driven, not code-driven.** The graph (states, transitions, preconditions, actions) is stored as data (JSON), not PHP classes — see "Rule & actor authoring UX" below for why this also matters for security, and how developers still get full PHP power when they need it.
- **Extensible via registries, not forks.** New action types, precondition types, and node types are addable by registering a class, the same way Backpack lets you register new field types — a downstream dev should never patch the engine's core to add one.
- **Backpack-native where it fits, plain Laravel where it doesn't — all inside the package, not `app/`.** The instance inspector and audit log are Backpack CRUDs shipped from `packages/workflow`, reusing existing plumbing: `spatie/laravel-permission` via `Backpack\PermissionManager`, Laravel's `Notification` system (the pattern already used in `app/Notifications/PasswordChangedNotification.php`), and the queue configured in `config/queue.php`. The **canvas/inspector editor itself is explicitly not required to be a Backpack CRUD or custom field** — it's a full-page, highly interactive drag-drop experience that doesn't naturally fit a form-field container, so it's its own plain Laravel route/controller/Blade views/JS within the package, only linked to from the `WorkflowDefinitionCrudController`'s list.
- **Events, not just registered actions, as an extension point.** Every transition dispatches a standard Laravel event so a downstream dev can hook in with an ordinary listener (e.g. `Event::listen` in their own `EventServiceProvider`) instead of always having to register a formal action type — see "Events & programmatic triggering" below.
- **Token-based execution, not a single "current state."** To support parallel branches, an instance's position is one or more active *tokens* (the standard BPM approach — see Core data model), not a single `current_node_id` column.
- **Versioned and safe to edit live.** Editing a graph must never corrupt an in-flight instance; instances pin to the version they started on.
- **Auditable by default.** Every transition, action firing, and manual override is logged.

## Core data model

| Table | Purpose |
| --- | --- |
| `workflow_definitions` | One row per workflow "template": name, target model class, current published version pointer. |
| `workflow_definition_versions` | Immutable snapshots of a definition's graph JSON (nodes + edges), one per publish. Instances pin to a specific version row. |
| `workflow_instances` | One row per (model record, workflow definition) — the version it's running on, overall status (active/completed/cancelled). Polymorphic (`workflowable_type` + `workflowable_id`). |
| `workflow_instance_tokens` | One row per active "position" within an instance (status active/consumed). A linear workflow has exactly one active token at a time; a fork node spawns one token per outgoing branch; a join node consumes all its expected incoming tokens and emits one outgoing token. This is what makes parallel branches possible without redesigning the model later. |
| `workflow_instance_history` | Append-only audit log: instance id, token id, from-node, to-node, triggered-by (user/system/timer/webhook), actor id, timestamp, captured `inputs` payload. |
| `workflow_timers` | Scheduled/pending timer entries per token (node id, fire-at, fired-at nullable, optional `stage` label for escalation chains) — scanned by a scheduled command, or dispatched as delayed jobs. |
| `workflow_instance_pending_actors` | Denormalized: for each active token with an outgoing manual edge, one row per resolved eligible actor (`role_id`, `permission_id`, or `user_id`). Recomputed whenever a token enters a node. Lets the instance inspector answer "who can act on this?" via a cheap indexed query instead of evaluating actor rules live. |

## Graph shape (the JSON a definition version stores)

- **Nodes** = states, plus two structural node types for parallel work: `type: 'state' | 'fork' | 'join'`.
  - `state` nodes carry a **field policy**: an ordered list of per-field override entries — `{field, visible, label, type, readonly, custom_field_definition}` — applied to the target model's Backpack create/update form whenever a token sits there. `visible` (boolean) replaces the originally-planned three-state `edit`/`readonly`/`hidden` mode with two independent booleans (`visible` + `readonly`), matching the field-policy editor's actual "Show" switch + "Readonly" checkbox columns; `label`/`type` let a state override how a field renders, not just whether; `custom_field_definition` is a literal-PHP-array escape hatch (parsed by `CustomFieldDefinitionParser`, never `eval`'d as freeform code — see "Rule & actor authoring UX") merged over the generated field config last, for anything the simple columns don't cover (`options`, `tab`, `wrapper`, etc.). E.g. "while `pending_review`, the reviewer sees `notes` editable and everything else read-only." Fields not listed fall back to a definition-level default (`config('workflow.default_field_mode')`, currently `readonly`). A state node also carries optional `header_view`/`footer_view` Blade view names, rendered above/below its form.
  - `fork` nodes have multiple outgoing edges that **all** fire at once, each spawning its own token (parallel branches — e.g. "notify legal" and "notify finance" happen simultaneously).
  - `join` nodes wait for every expected incoming token before consuming them and emitting one outgoing token (e.g. "proceed once both legal and finance have signed off").
  - **Conditional branching** is not a separate concept: it composes from a `fork`/`state` node with several `automatic` outgoing edges, each gated by a different precondition — only the edge whose precondition passes fires. This avoids inventing a second branching mechanism.
- **Edges** = transitions between two node ids. Each edge carries:
  - `trigger`: `manual` (record button / bulk action), `automatic` (fires immediately once its precondition passes), `webhook` (fired by an inbound signed request against a specific instance), or `timer` (fired when its `workflow_timers` entry is due).
  - `preconditions`: a **tree**, not a flat list — `{op: 'and'|'or', children: [...]}` nesting down to leaves like `{type: 'field_equals', field: 'status', value: 'approved'}` — evaluated via the registered precondition-type below. This covers grouped/OR logic without a second data shape.
  - `actor_rule` (manual triggers only): `{roles: [...], permissions: [...], users: [...], match: 'any' | 'all'}` — who may trigger this edge. Supports a role, several roles, a permission, several permissions, or a specific named user, combinable (e.g. "any of these two roles, OR this specific user").
  - `surfaces`: which UI entry points can fire this edge — `record_button`, `bulk_action`, or both. Ignored for non-manual triggers.
  - `requires_confirmation`: a checkbox in the edge inspector — when set, clicking the transition first shows a simple yes/no "are you sure?" prompt (this repo's existing bulk-delete confirm dialog is the precedent) before it fires. Independent of `inputs`: a transition can require confirmation only, capture `inputs` only, both (confirm, then show the input form), or neither.
  - `inputs`: an optional ordered list of **real Backpack fields** (any registered field type — text, textarea, select, date, whatever the target model's own form already uses), each with a `mode` of `edit` or `readonly` — conceptually reusing the same per-field override idea as a node's field policy (not necessarily its exact table shape, which has since grown visible/label/type/readonly/custom_field_definition columns — the edge `inputs` builder should be designed against whatever that editor looks like when built, not against this doc's original simpler sketch). It isn't limited to "one remarks box": a rejection transition might show a readonly summary field (e.g. the amount being rejected, for context) alongside an editable `rejection_reason` textarea, in one form. Editable inputs are captured and always land in `workflow_instance_history.payload`; any input (editable or the readonly ones, which are typically sourced straight from the record) can optionally map to a real model column via `store_as`. A `presentation` option (`modal` | `inline`) lets the developer choose whether this form pops up as a modal at the moment the transition is triggered, or is appended as a section at the end of the record's edit page (so the user fills it in as part of the normal save flow, without an extra dialog) — set per edge, since a quick single-field remark suits a modal but a denser multi-field capture may read better inline.
  - `actions`: an ordered array of registered action-type references + params (send email, fire notification, start timer, call webhook, custom) — params can reference values captured via `inputs`.
  - A `start_timer` action can declare a **chain of stages** (`[{after: '24h', action: 'send_notification', ...}, {after: '48h', action: 'send_notification', to: 'manager', ...}, {after: '72h', action: 'auto_transition', edge: '...'}]`) — this is how SLA escalation is expressed, as chained timer stages rather than new infrastructure.

## Rule & actor authoring UX (why not raw PHP in the editor)

Direct question raised: how does a developer input rules in the editor — plain PHP code?

**No** — the visual editor never accepts freeform code that gets stored as data and executed later. Storing arbitrary PHP text in the database and `eval`-ing it at runtime means anyone who can edit a workflow graph (potentially through a compromised admin account, not just a trusted developer) gets arbitrary code execution. That's an unacceptable trade for a framework meant to be a secure starting point.

Instead, two paths, both already implied by the design above:

1. **Structured no-code rule builder (primary path).** Each registered precondition type declares its own small form (field picker + operator + value, or role/permission/user pickers for `actor_rule`) — visually similar to this repo's existing filter UI (the kitchen sink's `range`/`dropdown` filters), composed into the AND/OR tree via simple group/add-condition controls. This covers the large majority of real rules ("status equals X", "amount greater than Y", "user has role Z") with no code at all.
2. **`custom_callback` escape hatch (for real PHP power).** A precondition or action type that references a PHP class the *downstream developer* has already written and registered in their own app's service provider (the same registry mechanism as every other type). In the editor, this appears as a dropdown of already-registered callback classes — never a text box for typing code. Full PHP logic stays available, it's just declared in version-controlled application code instead of stored as executable text in the admin UI.

## Events & programmatic triggering

- **Every transition dispatches a Laravel event** — a `Transitioning` event before it commits (listeners can cancel it, e.g. a last-second guard) and a `Transitioned` event after, each carrying the instance, token, edge, resolved actor (or `null` for system/timer/webhook triggers), and any captured `inputs`. This is a second, lighter extension point alongside the registered action-type system: a downstream dev who just wants "send an email when an invoice hits `approved`" can write one ordinary listener in their own `EventServiceProvider` instead of registering a formal `WorkflowActionType`. The two mechanisms aren't competing — registered actions are for behavior defined *inside* the graph by whoever designs it (so a non-developer editing the canvas can attach them); events are for behavior a developer wires up in code, outside the graph entirely.
- **`transitionTo()` is a first-class programmatic API, not just what buttons call internally.** Backend code — a controller, a queued job, a service class, a payment-webhook handler — can call `$record->transitionTo($edgeId, $inputs = [], $actor = null)` directly to advance a workflow from outside the admin UI entirely (e.g. an external payment gateway's webhook controller advancing an invoice from `pending_payment` to `paid`). When called this way, the calling code is responsible for its own authorization context: passing an explicit `$actor` still runs that edge's `actor_rule` check against them, while omitting it (or passing a recognized "system" marker) skips the human `actor_rule` check — preconditions still run either way, since those guard data integrity, not who's allowed to click a button.

## Extensibility mechanism

- `WorkflowActionType` interface (with an optional `preview()` for dry-run mode, see below) + a registry (`WorkflowActionRegistry::register('send_email', SendEmailAction::class)`), resolved by string key — mirrors how Backpack resolves field/column types. Ship built-ins: `send_email`, `send_notification`, `start_timer`, `call_webhook`, `custom_callback`.
- `WorkflowPreconditionType` interface + a similar registry. Ship built-ins: `field_equals`, `field_in`, `custom_callback`.
- `actor_rule` (roles/permissions/users) is a built-in concept, not a registered type — it's fundamental to every workflow, unlike the genuinely extensible precondition/action types.
- Downstream devs register their own types in their own service provider — no engine files need editing.

All items below ship from `packages/workflow` per the Package structure section — nothing here requires new files under this repo's `app/` directory.

1. **`WorkflowDefinitionCrudController`** (Backpack) — a plain list/create (name, target model, description) of workflow templates; each row links out to the standalone editor below rather than embedding the canvas in a Backpack form.
2. **The canvas/inspector editor itself — a standalone module, not a Backpack CRUD/field.** Its own route (e.g. `admin/workflows/{definition}/design`), a dedicated controller, and its own full-page Blade view/JS (still Alpine-first, still no jQuery, to stay consistent with this codebase's direction — just not wearing Backpack's form/field chrome). Wraps a drag-drop JS flow library (Drawflow or Rete.js — dependency-free) with the node/edge inspector panels alongside it, and posts the serialized graph JSON to save a new `workflow_definition_versions` row. Includes a **"Test with a sample record" dry-run mode**: runs a real record through the graph without persisting instance state or actually sending emails/webhooks — actions render their `preview()` output instead.
3. **Node inspector — field-policy editor**: an "Edit" button on the state-node inspector opens a `modal-xl` window listing every field of the target model and its related models (columns discovered via `WorkflowModelFieldsController`, reflecting the model's public zero-arg relation methods) in a reorderable (drag-handle, native HTML5 drag-and-drop) table: **Column** (readonly `table.column` display), **Show** (visibility switch), **Label** (text), **Type** (every registered Backpack field type), **Readonly** (checkbox), and **Custom field definition** (a monospace textarea holding a literal PHP array, collapsible between 1 and 10 rows, validated server-side on Save — see `CustomFieldDefinitionParser`). No manual add/delete-row controls: the row set is exactly the model's discovered fields, policy only overrides them. An "Import from" control in the modal footer copies another node's entire field policy in one action (with a confirm prompt). The node inspector also exposes plain `header_view`/`footer_view` text inputs alongside the field-policy button.
4. **Edge inspector**: precondition tree builder (AND/OR groups), the `actor_rule` picker (multi-select role/permission/user fields, each backed by Backpack's relationship-field pattern), the `inputs` builder (pick one or more of the target model's real Backpack fields and set each to edit or readonly — reusing the same field-picker UI as the node inspector's field-policy editor), `surfaces` picker, and the chained-timer/escalation builder for `start_timer` actions.
5. **A `HasWorkflow` trait** — added to any Eloquent model to get `->workflowInstance()`, `->transitionTo($edgeId, $inputs = [])`, `->availableTransitions()`.
6. **A generic `workflow` column/field** for any CRUD showing an entry's current state(s) (badge per active token) plus buttons for each `record_button` transition available to the logged-in user (actor-rule-checked, precondition-checked), prompting for `inputs` when required.
7. **A field-policy resolver hooked into `setupCreateOperation`/`setupUpdateOperation`** applying the current node's field policy before Backpack renders the form.
8. **A `WorkflowBulkTransitionOperation`** — same shape as this repo's existing `BulkDeleteOperation` (wired into `KitchenSinkCrudController`): select rows, pick a transition with the `bulk_action` surface, per-record actor/precondition checks, succeeded/skipped-with-reason summary.
9. **`WorkflowInstanceCrudController`** (read-mostly) — all in-flight/completed instances across every model, full history (including captured `inputs`), the manual-override escape hatch (force-advance a token, itself logged), and visibility into stuck joins (tokens waiting on a branch that never arrived).
10. An inbound **signed webhook route** per instance/edge for externally-triggered transitions.
11. A scheduled Artisan command scanning `workflow_timers` for due entries (including escalation stages) and firing them.

## Delivery

All implementation work for this feature happens on a dedicated branch, `feat/workflow`, created off `main` — not directly on `main` — given the size and multi-session nature of this build. (Using `/` rather than a literal `:` in the branch name — colons are technically legal in git branch names but collide with push-refspec syntax and trip up some tooling, so `feat/workflow` is the safe equivalent of what was asked for; flagging this rather than silently doing something else.) This document is the architecture this branch's implementation follows; a more granular step-by-step build plan is scoped from it before code is written, per the note at the top of this document.

## Verification (once a build plan follows this architecture)

- A throwaway model in this repo's own kitchen sink (or a small dedicated demo model) exercising: a manual transition gated by an `actor_rule` combining a role and a named user, an automatic transition gated by a nested AND/OR precondition tree, a fork into two parallel branches that a join waits on, a timer with an escalation chain, and an email action — proving the full loop end-to-end.
- Confirm a state's field policy changes what's visible/editable/labeled on that model's Backpack edit form when a token sits in that node, including a `custom_field_definition` override taking effect (and a non-literal-array value being safely ignored rather than executed).
- Confirm a transition with required `inputs` blocks submission until filled, and the captured value lands in both `workflow_instance_history` and (when `store_as` is set) the model's own column.

- **Designer bug: the inspector panel and settings modal could freeze their own scroll.** Opening a select2 dropdown binds a namespaced `scroll` listener onto every scrollable ancestor that snaps it back to where it was when the dropdown opened; that listener is only removed by select2's own `close()` teardown, which `destroy()` never runs — so destroying a widget whose dropdown was still open (exactly what removing a selected chip does) froze the ancestor's scroll forever. New `destroySelect2Safely()` closes before destroying. Alpine's `x-html` compounded it by re-rendering (and wiping) the inspector's innerHTML on *every* field edit without going through our own re-init path at all, so both `renderNodeInspector()`/`renderEdgeInspector()` now run the same cleanup at their very top — the one choke point guaranteed to run first whatever triggered the re-render. The settings modal's own handlers also moved from `initActorSelect2()` to the full `reinitSelect2Widgets()`.
- **Designer: detour-lane labels no longer overlap.** Orthogonal routing was refactored so both reasons an edge can't use the plain 2-bend path (a degenerate midpoint, or a straight path that would cut through an unrelated node) pick their horizontal offset from the *same* lane assignment instead of independently; since a lane is only ~24px wide and a label is 80–150px, each lane's label is additionally staggered onto its own row.
- **`WorkflowModelCallbackSearchController` validated the target model against the wrong source** — `EloquentModelFinder` only scans `app/Models`, so a workflow whose model lives in its own package (the Purchase Request demo's, for one) got an empty callback picker. It now accepts any class that is already some `WorkflowDefinition`'s target, matching the same fix made earlier to `WorkflowModelFieldsController`/`WorkflowActorSearchController`.
- **Demo: the `callbackFunction*` naming convention now applies to visibility callbacks too** — `PurchaseRequest::visibleToDepartment()` → `callbackFunctionSameDepartment()`, so every model-callback escape hatch (actor rules, preconditions, list visibility) is discoverable by the same prefix the designer's picker groups on.
- **Demo: the `draft` node's `amount`/`purpose` are now inline-editable** (`readonly => false`), making the requester's "fix it and resubmit" loop a live example of inline editing rather than a round trip through the model's own edit form. Covered by a new `PurchaseRequestInlineFieldEditTest` — that the fields render as real inputs with no Update access, that the `data-init-function` dispatcher is present so a money field actually submits what was typed, that a timeline entry records who changed what, and that a field *not* marked editable can't be updated this way even if it's submitted anyway.
